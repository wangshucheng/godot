## 一、整体评价

两份文档构成「基线分析 + 实施规格」完整闭环：
- `steel-echo-red-star.md`：架构对比与可借鉴性分级（A/B/C/D），结论严谨，避免无意义移植
- `mono_editor_spec.md`：基于 A/B 级清单的具体实施 spec，含全局约束、文件清单、验证计划

### 核心优点

1. **§0.2 全局约束**（移植纪律 6 条）质量极高——每条都有具体代码引用（`mono_icalls.cpp:2417`、`csharp_script.cpp:842`、`csharp_script.cpp:941-949`），体现了 WASM-safe 工程纪律
2. **优先级排序合理**：P1 (Export) → P2 (GlobalClass) → P3 (Signal) → P4 (BuildPanel) → P5 (Tool) → P6 (Watch) → P7 (Debugger)，符合「价值÷成本 + 依赖关系」原则
3. **B0 共享基础设施设计正确**：用 `mono_custom_attrs_from_member` + 字符串比较特性名，避免 C# 反射实例化（AOT 不友好），是正确的架构决策
4. **代码行号引用准确率 ~90%**：核对发现 `make_template` L1305、`get_built_in_templates` L1315、`ensure_project_file` L1431、`build_project` L1528、`get_property_type` L868、`debug_*` L156-165 全部对得上

### 主要问题

5 处假设偏差 + 8 处实施细节缺失，下文详述。

## 三、问题清单

### 🔴 P0（需修正的假设错误）

#### 问题 1：§1.2 SCsub 假设错误，且与 §0.2.5 自相矛盾

**spec 原文（§1.2）**：
```python
if env["tools"]:
    SConscript("editor/script_templates/SCsub")
```

**实际**：当前 SCsub **完全没有** `if env["tools"]:` 块，所有源文件（含 `mono_export_plugin.cpp`、`editor/bindings_generator.cpp`）都无条件列入 `mono_sources`。TOOLS 守卫发生在 C++ 源码内部（`#ifdef TOOLS_ENABLED`）。

**spec 原文（§0.2.5）**：
> "当前模块 SCsub 不做条件编译（SCsub:21-35），editor-only 代码一律用 #ifdef TOOLS_ENABLED 包裹"

**矛盾**：§0.2.5 明确说"SCsub 不做条件编译"，但 §1.2 又要加 `if env["tools"]:` 块。

**建议**：统一为「**SCsub 层不做条件编译，所有新增 editor 源文件直接加入 mono_sources，C++ 内部用 #ifdef TOOLS_ENABLED 守卫**」。`editor/script_templates/SCsub` 应改为在主 SCsub 中无条件 `SConscript()`（其内部自行判断 tools），或在主 SCsub 中用 `if env["tools"]:` 但同步修订 §0.2.5 表述。

#### 问题 2：§2.A3 sanitize 抽取方向描述失准

**spec 原文**：
> "utils/path_utils.cpp 全量替换为旧版（258 行）...`get_csharp_project_name` 保留旧版签名，但行为对齐当前 `get_safe_project_name`（csharp_script.cpp:174-185）"

**实际**：`csharp_script.cpp:149-185` 中 `sanitize_project_name` 和 `get_safe_project_name` 都是 **static 内嵌函数**，未在 `utils/path_utils.cpp` 中。当前 `path_utils.cpp` 只有 61 行，且其 `get_csharp_project_name` 实现已与 csharp_script.cpp 的 `get_safe_project_name` 不同。

**建议**：
1. 明确说明 `sanitize_project_name` 是从 `csharp_script.cpp` **抽出**到 `path_utils.cpp`（而非"对齐"）
2. 同步删除 `csharp_script.cpp:149-172` 的 static 实现，改为 `#include "utils/path_utils.h"` 调用
3. 明确 `mono_export_plugin.cpp:14-37` 的第二份 sanitize 也一并删除

#### 问题 3：§4.P4 EditorDock API 需验证存在性

**spec 原文**：
> `class MonoBuildPanel : public EditorDock` ... `EditorDockManager::get_singleton()->add_dock(panel)`（参照 `shader_file_editor_plugin.cpp:325-329`）

**核查结果（2026-07-25）**：`godot4.7_mono/editor/docks/editor_dock.{h,cpp}` 与 `editor_dock_manager.{h,cpp}` **存在**，API 可用，spec 假设成立。

**保留建议**：在 spec 中加注「已核查 EditorDock API 存在于 `godot4.7_mono/editor/docks/`，可放心使用」。

### 🟡 P1（实施细节缺失）

#### 问题 4：§3.2 B0 类型映射覆盖范围不清

**spec 原文**：
> "mono_type_to_variant_type(MonoType*) 覆盖：bool/int 全宽/float 全宽/string/全部数学值类型（与 mono_variant 缓存类比较）/enum→INT/Object 派生→OBJECT/Array·Dictionary 包装→ARRAY·DICTIONARY"

**问题**：
- 当前 `get_property_type` L868-901 只覆盖 5 类（BOOL/I4/R4/R8/STRING/OBJECT），未递归父类
- "全部数学值类型"具体指哪些？Vector2/Vector3/Color/Rect2/Transform2D/Transform3D/Quaternion/AABB/Plane/Basis？
- 这些类型在 glue 中是 struct 还是 class？`mono_type_get_type()` 返回 MONO_TYPE_VALUETYPE，需进一步 `mono_class_get_type` + 类名比较

**建议**：在 §3.2 增加类型映射表，明确列出 Godot 数学类型与 Variant::Type 的对应关系。

#### 问题 5：§4.P1 命名决策（PascalCase vs snake_case）需说明与原生 .NET 模块一致性

**spec 原文**：
> "Inspector 显示名直接用 C# 成员名（PascalCase），与 set/get 三级查找键一致"

**评价**：决策本身合理（C# 习惯 PascalCase），但需补充：
1. 与 Godot 官方 .NET 模块（旧方案）的一致性说明——旧方案也是 PascalCase
2. 序列化兼容性：场景保存时属性名会写入 .tscn/.scn 文件，PascalCase 与 GDScript 脚本的 snake_case 不互通——这是设计选择，需文档化
3. 风险：若用户混用 GDScript + C#，跨脚本引用属性会因命名差异失败

#### 问题 6：§4.P2 文件名==类名约定风险

**spec 原文**：
> "按文件名匹配类名（与 _parse_base_class 一致的命名约定：文件名==类名）"

**问题**：C# **不强制**文件名==类名：
- 一个 .cs 文件可含多个类（partial class 拆分、内部类）
- 文件名可与类名不同（如 `MyNode.v2.cs` 含 `MyNode` 类）

**建议**：
1. v1 明确文档说明此限制（"C# 类必须定义在与类名同名的 .cs 文件中"）
2. v2 用 `mono_image_get_table_info(image, MONO_TABLE_TYPEDEF)` 迭代 + `MonoMethod* debug_info` 查源文件路径（需 .pdb 支持）

#### 问题 7：§4.P7 mono_debugger_agent 启用条件未核对

**spec 原文**：
```cpp
const char *options[] = { "--debugger-agent=transport=dt_socket,server=y,suspend=n,address=127.0.0.1:55555" };
mono_jit_parse_options(1, (char **)options);
```

**风险**：
1. Mono 静态库构建时需启用 `--enable-debug` 与 `--with-monodbg`，否则 sdb agent 不可用
2. 当前 `mono/libs/web/wasm/*.a` 是 WASM 静态库（不含 sdb），但 P7 说"仅桌面"——需确认桌面 Mono 静态库（`mono/lib/` 或系统安装）是否启用了 sdb
3. `mono_jit_parse_options` 必须在 `mono_jit_init_version` 之前调用——spec 已注明，但需核对 `mono_host.cpp` 的初始化顺序是否允许插入

**建议**：P7 实施前先做 spike——在 `mono_host.cpp` 加 `mono_jit_parse_options` 试运行，验证 sdb 是否可附加。

#### 问题 8：§5 验证计划缺 WASM 端 TOOLS 裁剪回归

**spec 原文**：
> "编译验证：scons platform=web target=template_release mono_wasm=yes（验证 TOOLS 裁剪后 WASM 构建不受 B 级影响）"

**问题**：仅"编译验证"不够。B 级改动会在 `csharp_script.cpp` 等文件加大量 `#ifdef TOOLS_ENABLED` 块，需确保：
1. WASM 构建产物中无 TOOLS 相关符号（`nm` 检查）
2. WASM 端 23 场景回归测试全 PASS（当前基线 205/205 断言）
3. WASM 包体积无显著增长（< 1% 波动）

**建议**：验证表新增 WASM 回归测试行。

### 🟢 P2（建议优化）

#### 问题 9：A2 CodeCompletion 消费方不明

**spec 原文**：
> "同时在 CSharpLanguage 中不做接线（当前无内建脚本编辑器补全框架对接需求）"

**问题**：若不接入 CSharpLanguage，A2 的 icall + glue API 就位后无人调用，价值为零。

**建议**：
1. 明确 A2 的实际消费方（外部 IDE 插件？未来自建 C# 脚本编辑器？）
2. 若无明确消费方，建议将 A2 降级为 C 级（延后到 GodotTools 移植时一起做）
3. 或在 A2 末尾加「最小消费示例」：在 `ScriptTextEditor` 的 completion provider 中调 `CodeCompletion.Request`

#### 问题 10：linker.xml 更新清单不完整

**spec 原文（§0.2.6）**：
> "glue 新增的 C# 类型必须加入 modules/mono/glue/linker.xml 的 preserve 清单"

**问题**：未列出 B0 新增的具体类型。

**建议**：在 §3.1 末尾明确列出需加入 linker.xml 的类型清单。

#### 问题 11：P5 [Tool] 脚本崩溃隔离缺失

**spec 原文（§4.P5.4）**：
> "tool 脚本异常不崩编辑器是验收项，发现崩溃路径必须就地修复"

**问题**：未说明如何隔离。当前架构 `mono_domain_assembly_open` 加载到 root domain，[Tool] 脚本崩溃会直接影响编辑器进程。

**建议**：
1. 评估是否需要子 domain 隔离（`mono_domain_create_appdomain`）
2. 或在 `invoke_method` / `notification` 外层加 `mono_runtime_set_pending_exception(nullptr)` 清理
3. 在 P5 验收项加「fuzz 测试」：构造 10 个异常脚本（空引用/除零/栈溢出/无限循环），确认编辑器不崩

#### 问题 12：B0 collect_signals 委托约定需明确

**spec 原文（§3.1）**：
> "[Signal] 约定沿用旧方案：嵌套委托命名为 <SignalName>EventHandler"

**建议**：在 §3.2 `collect_signals` 实现说明中加：
- 委托必须嵌套在类内部（`mono_class_get_nested_types`）
- 父类必须是 `MulticastDelegate`（`mono_class_get_parent` 检查）
- `Invoke` 方法签名构建 `MethodInfo`（参数名从 `mono_method_signature` + `mono_parameter_get_name` 获取，参数类型走 B0 类型映射）

## 四、`steel-echo-red-star.md` 评审

### 优点

1. **「一句话结论」精准**："两者不是同一模块的两个版本，而是两套架构"——准确点明无法整体移植
2. **A/B/C/D 四级分类合理**：A 级（纯 C++/资源文件，零耦合）✓；B 级（需按反射/icall 路线重写）✓；C 级（大工程，需评估收益）✓；D 级（架构冲突不可借鉴）✓
3. **§2.3 脚本系统缺口清单**与 `csharp_script.h` 实际空实现完全吻合（已核对）
4. **§4 建议路径**「A 级全拿 → B 级 P1-P3 → P4-P6 → P7」与 spec 的优先级一致

### 问题

#### 问题 13：文档未更新实施状态

**建议**：在文档头部加「更新说明」，标明已立项 spec 文档实施 A 级 + B 级。

#### 问题 14：§3 B 级 P4 排序与 spec 不一致

**steel-echo §3**：
> "P4 — 构建面板...完全独立于 P1–P3，可穿插做"

**spec §4.P4**：
> "v1 仍同步阻塞编辑器，UI 文案提示；异步化列为后续优化，不做"

两处都把 P4 定位为"可穿插"，但 spec 又说"不做异步化"，意味着 P4 完成后编辑器仍会卡顿。建议在 spec 中明确「P4 同步阻塞是已知缺陷，列入 v2 改进项」。

#### 问题 15：§3 C 级 2 SourceGenerators 评价过于保守

**原文**：
> "桥接类生成器（ScriptMethods/Properties/SignalsGenerator）深度绑定旧 Bridge API，不可直接用"

**评价**：虽然不可直接用，但「编译期生成替代反射」是 WASM 性能优化的关键方向（当前 `Object_Call` 动态分发在 WASM 解释器下有性能损耗）。建议改为：
> "桥接类生成器不可直接用，但其编译期生成思路是 WASM AOT 性能优化的方向，列为 v3 探索项"

## 七、总体结论

两份文档是**高质量的设计产物**，体现了对 Mono embedding、WASM AOT、Godot 脚本系统的深度理解。全局约束（§0.2）尤其出色，是项目累积踩坑经验的结晶。

**主要风险集中在实施细节**而非架构方向：
- SCsub 假设偏差（P0，已修订）
- B0 类型映射覆盖范围（P1，已修订）
- EditorDock API 存在性（P0，已核查通过）
- P7 sdb 可用性（P1，已加前置 spike）

**建议下一步**：
1. 修订 spec 中的 P0 问题（3 处）✓
2. 补充 P1 实施细节（类型映射表、WASM 回归、sdb spike）✓
3. steel-echo 文档加更新说明 ✓
4. 修订完成后即可启动 A 级实施（A1 模板扩充是最低风险切入点）
